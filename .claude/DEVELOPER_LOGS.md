## 2026-09-13: The spike works, and scrolling lied

We pointed headless Chromium at a 127-track IDM playlist, logged out, and watched the web player's own API calls go by. One of them, `fetchPlaylist`, had everything the spec wants: description, followers, owner ID, and an `addedAt` on every track. It only covered the first 25 tracks, though.

The first fix was scrolling so the player loads the rest, and it seemed to work. Counting the captured tracks told a different story: 108 of 127. The player had quietly skipped a whole page. A pipeline built on that would have reported playlists as dead when their newest adds were simply never fetched. In this playlist the two most recent adds were buried mid-list.

So we stopped scrolling. `spike/fetch_playlists.py` now loads the page once, keeps the auth headers and persisted-query hash from the player's own request, and asks for each page by offset. Result: 10 of 10 real playlists fetched completely, from 21 to 5,931 tracks, no login.

Two things this showed:
- **Big playlists are slow.** A 5,931-track list took over three minutes at one page per second. Stage 3 needs a track-count ceiling or an early stop.
- **Search results skew dead.** Only 2 of the 10 would pass the Alive rule, so neighbour discovery is doing more of the work than the spec implies.

We also looked at Spotify MCP servers and the Claude Spotify connector. Both sit on the official Web API under a personal login, which the spec excludes. Neither would be available to an unattended nightly job anyway, so they aren't part of the design.

## 2026-09-13: Finding a curator's other playlists

Neighbour discovery depends on one question: what else has this curator made? The first probe of a profile page found nothing, and the screenshot showed only a footer, because it was taken after scrolling to the bottom. Taken before scrolling, it showed the whole profile: arsendis, 402 public playlists.

The data turned out to be hidden in plain sight. The capture filter included the right host, but the web player asks for **protobuf** and the probe only kept responses it could parse as JSON. When the same endpoint is asked for `application/json`, it returns JSON.

- **A curator's public playlists aren't all theirs.** 30 of arsendis's belong to other people, Spotify included. Filter on `owner_uri`. The others are interesting too, since they show which curators this curator follows.

Still open: comparing Serper and Brave, which needs API keys. `spike/compare_search.py` is written and exits cleanly without them. Added `.gitignore` and `.env.example` so keys stay out of the repo.

## 2026-09-13: The YAML file becomes a web app

The spec imagined the artist profile as a small file, edited rarely. Jarred wants more than that: several profiles, each with its own genres, reference artists and search terms, edited through a web page, with the system proposing new search terms for him to approve.

That changes the shape of the build more than any single feature:
- **Config moves into the database.** Profiles, genres, artists, anti-signals, tracks and search terms become tables the pipeline reads and the web app writes.
- **Fit is now per profile.** A playlist can be a great match for one project and wrong for another. Liveness and pay-to-play checks don't depend on the profile, so they stay per playlist. Fit gets its own table.
- **Search terms have a lifecycle:** proposed, active, paused or rejected, plus an origin (manual or suggested). A suggestion never runs until Jarred approves it, and a rejected term is never proposed again.

Stack for the web app: **FastAPI, Jinja2 and HTMX**, in the same Python codebase and against the same models as the pipeline. A separate JavaScript frontend would mean two languages, two builds and two sets of models for what is essentially a set of forms and an approval queue. HTMX still gives inline editing, partial updates and transitions.

Plan restructured: settings web app is Stage 2, and search-term suggestions are folded into the feedback stage. Stage 1 gets a YAML import command so pipeline work can start before the web app exists. New open questions: should the digest and verdict buttons live in the web app too, how is it reached (localhost or Tailscale), and can one curator be pitched for two profiles.

## 2026-09-13: Half on Vercel, half at home

Jarred asked whether the whole thing could live on Vercel with a linked Neon database. The honest answer was half of it.

The web app is a natural fit. FastAPI runs on Vercel's Python runtime, Neon links in through the integration, and the app can be reached from anywhere without opening a port at home.

The pipeline is not. A Vercel function can run for 5 minutes on Hobby and 13 on Pro (30 in beta), and the Stage 0 quality check alone took 35 minutes. More important is where the traffic comes from. The spike succeeded from a home IP, while Spotify's page loads reCAPTCHA Enterprise, and cloud-server IPs are exactly what bot detection is tuned to distrust. Moving the fetch to Vercel would trade a free, proven setup for a fragile one.

So the system splits. Vercel serves the web app. The Mac Mini runs the pipeline under launchd and only ever reaches out, to Neon, Spotify and the APIs. Neon is the only thing they share. Three details make the split usable:
- **"Run now"** can't call the Mac Mini, so it writes a `run_requests` row that a small poller on the Mac Mini picks up within minutes.
- **A heartbeat** in the `runs` table lets the web app warn when the Mac Mini has gone quiet. Otherwise a switched-off machine would just look like a slow night.
- **Secrets stay where they're used.** Serper, Brave and Anthropic keys never go to Vercel. The web app gets its own Neon role, a pooled connection string, and a bundle with no Playwright in it.

Because the app is now on the public internet, Stage 2 gained real security criteria: session on every route, CSRF, rate-limited login, and tests that prove the door is locked. The remaining open question is how Jarred wants to log in.

## 2026-09-13: Stage 1 foundations, and the role that would have been a superuser

Stage 1 is where the system's promises turn into things Postgres enforces. The headline is an EXCLUDE constraint on `outreach`: the same curator's `[digest_date, digest_date + 90)` ranges may not overlap, across every profile. The tests passed first time, which proves nothing on its own, so a mutation check dropped the constraint and tried again. With the constraint, a second entry within 90 days is refused. Without it, the entry goes straight in. The guarantee lives in the database, not just in hopeful Python.

Around it: contact normalisation (every spelling of a curator collapses to one key), settings that never echo a URL, a validated profile YAML format with a safe re-import, exclusion rules for Jarred's verdict decisions, and a least-privilege grants module. Everything was built test-first against a real Postgres 18 in Docker, once Docker Desktop got its admin password.

Two small traps along the way. A shell variable holding the list of test files didn't word-split in zsh, so pytest ran *nothing* while `| tail -1` hid the exit code. Now every chain uses `set -o pipefail` and explicit paths. And `normalize_text` had to move out of `profile_config.py`, because that module imports `yaml` and Vercel doesn't install it.

The bigger catch came from reading Neon's docs before creating the web and pipeline roles. **Roles made in the Neon console are added to `neon_superuser`**, which includes `pg_write_all_data`, `CREATEROLE` and `BYPASSRLS`. The plan said "create them in the console, then grant least privilege". That would have produced a public-facing web role able to write every table, with the grants as decoration. Roles created with SQL start with nothing. So the pipeline CLI creates them itself, with a generated password hashed to SCRAM on the client, so the plaintext never crosses the wire.

## 2026-09-13: Neon wants the password, not the hash

That last sentence didn't survive contact with Neon. Against local Postgres, `db create-roles` passed every test. Against Neon it failed with one unhelpful word: `InternalError`.

The first fix was to the diagnosis, not the code. Every `CREATE ROLE` variant succeeded on Neon inside a transaction: the exact statement, attributes only, hashed password, plaintext password. So did every GRANT, replayed one by one. Only the commit failed, and the real message was there all along: *Received HTTP code 400 from control plane: "Neon only supports being given plaintext passwords."* Neon syncs roles to its control plane when the transaction commits, and it refuses a pre-hashed SCRAM verifier.

Two changes came out of it:
- **Passwords are now sent as generated.** They're still 256 bits, URL-safe base64, over a TLS connection (`sslmode=require`), and Postgres stores them as SCRAM. A new test listens to the SQL actually sent. Local Postgres accepts hashes, so only that kind of test can pin the Neon requirement down.
- **CLI database errors now show the SQLSTATE and the first line of the server's message.** Password clauses, SCRAM verifiers, connection URLs and `npg_` strings are masked, and the SQL statement is never included. "InternalError" alone had hidden a one-line answer.

Nothing was left behind by the failed attempt: the transaction rolled back, the output file was never kept, and a throwaway probe role was created, confirmed and dropped.

The foundation is built around one idea: on the public internet, the safe failure is a closed door with a sign on it. Every setting is required, so an app that doesn't know its allowed user refuses to run. If settings are missing, Vercel still gets an importable app. It answers `/health` with `configured: false` and shows a "not configured" page, instead of a stack trace nobody would see. The dark studio design is plain CSS on tokens: near-black ground, a single lime accent, a mono eyebrow, generous space, a short entrance motion, visible focus rings, and respect for reduced motion. Tailwind was dropped, because a CSS build on Vercel's Python builder was a moving part with no payoff at this size. Headless Chromium screenshots at 1280px and 390px confirmed it reads as intended. The console's only 404 was the deliberately missing test page.

## 2026-09-13: Stage 2b, a front door with one key

Sign-in is designed default-deny. One middleware sits in front of every route and lets through only `/health`, `/login`, the two OAuth routes and `/static`. Any page added later is protected without anyone remembering to protect it. A signed-out browser is sent to `/login?next=…`. An htmx request gets a 401 and an `HX-Redirect` instead, because redirecting a partial swap would paste a login page into the middle of a table.

Authlib does the cryptography: OAuth state, ID-token signature, nonce. Reading its installed source (the docs URL was dead) confirmed it keeps state in the session and puts verified claims in `token["userinfo"]`. Our callback holds the policy. The email must be *verified* and on `ALLOWED_EMAILS`. The session is cleared and rebuilt on sign-in, so a planted session can't carry over. `next` may only be a path on this site: `//evil`, `/\evil`, schemes and control characters all become `/`. Refusals render a 403 page. A broken exchange renders a 400 "didn't complete" page, never a traceback. Vercel's proxy can present the request as http, so the callback URI is forced to https in production, where Google insists on an exact match.

CSRF uses a per-session token that htmx sends as `X-CSRF-Token` from the page's `hx-headers`, compared in constant time for every unsafe method. One ordering bug was designed out before it shipped: security headers were the innermost middleware, so the guard's redirects would have gone out without a CSP. They are now outermost.

Unit tests use a fake Google. The proof that the parts fit came from a real browser: headless Chromium signed in through a local stand-in provider, landed home, clicked **Sign out**, and ended on `/login` at both 1280px and 390px, with zero console errors. A stranger's address landed on "This account is not allowed". That run exercises htmx, the CSRF header and the CSP together, which unit tests can't do.

## 2026-09-14 (before dawn): The whole chain, run for real

With search, discovery, fetching and judging all in place, `pipeline/qualify.py` became the part with opinions. A playlist is alive if a track went in within 60 days and at least three in 180. It's real unless its description sells placements, or it has a vast following on a dozen tracks. It fits a profile by how many reference artists are already on it: three or more is top tier, one or two acceptable, and any anti-signal is a veto. "EDM" vetoes "EDM mix" but not "Edmonton". The verdict order is deliberate, because the recorded reason decides whether it's ever re-checked: Spotify-owned (new migration 0002), then pay-to-play (both permanent), then dead (re-checked in 90 days), then no fit.

`pipeline/evaluate.py` fetches candidates oldest first and judges each against every active profile in one pass. It stores one curator per Spotify owner and commits after every playlist. Failures follow their meaning: a missing playlist is dead, a timeout is retried next run, and being blocked stops everything at once. `pipeline.cli run` and `report` wrap it for a human.

Then it ran against the live internet, using a local database and the stand-in example profile. Five search terms found 274 playlists, 261 of them new. Fifteen fetches completed in three minutes, including one Spotify HTTP 500 that the retry quietly absorbed. **None qualified.** That's worth checking rather than celebrating or panicking, so every rejection was inspected. Nine were dead, several for three to five years, including an "IDM soft sound" playlist carrying four reference artists that nobody has touched since 2021. Six were alive but off-genre: jazz piano for sleep, Beatport's indie dance chart, a lo-fi label's dark ambient. The rules did their job; search results just skew old and adjacent, exactly as Stage 0 warned. A 150-playlist batch is running to see what the real yield looks like at scale.

## 2026-09-14 (morning): A floor under "qualified"

Jarred settled the first gap in one line: under 50 followers isn't worth a pitch. He also wanted the number in the web app, per profile, not buried in code. So `profiles.min_followers` (migration 0003) defaults to 50, and the settings form edits it. It accepts any whole number from 0, meaning no floor, to a million.

The floor applies only after fit. A playlist that fits but is too small gets its own rejection, `too-small`, rather than being lumped in with `no-fit`. The difference matters in 90 days. Small playlists grow, so `too-small` is re-checked like `not-alive`. An anti-signal still vetoes outright, and if no profile fits at all the reason stays `no-fit`, because that is the truer story. Each profile uses its own floor, so a niche profile set to 10 can take a playlist that the main profile turns away.

Leaving the field blank keeps the current value. That way an older form, or a future caller that only renames a profile, can't quietly reset the floor to zero.

The second gap, owners who aren't people, gets no rule of its own. Jarred's view is that a lead with no reachable human is no lead. Stage 6's contact research will mark those `no-contact`, so Chosic and volt.fm drop out for the same reason as an anonymous personal playlist.

## 2026-09-14 (mid-morning): Reading the description first, and a schema that got ahead of itself

Contact research starts where the spec says the answers most often are: the curator's own description. `pipeline/contact_extract.py` pulls out emails (including `demos [at] label [dot] com`), handles, form links and Discord invites. It also lists the links worth following next. Its tests use formats copied from last night's real playlists, among them `Submissions: PlaylistsByElise@gmail.com`, `Follow @laguerradelasgalaxiasvinyl on Instagram` and `Submit tracks for consideration: https://discord.gg/...`. There are traps too: `record label @ www.site.org` is a website, not a handle, and `v0.2` is not a domain.

Order is the trick. Emails are found and blanked out first, so `gmail.com` never shows up as a site to visit. Web addresses come next, so `instagram.com/name` becomes a route and isn't read twice. Handles are last, and they only count when the text names the platform. A bare `@someone` could belong to anyone, anywhere. None of the 12 playlists that qualified last night had contact details in its description, so most of the yield will depend on the research agent, just as the spec warned.

## 2026-09-15: Making room for more than one artist

Jarred wants to invite other artists, and a shared app would have meant a shared inbox once email pitching lands. So before any email work, Noble Hunter learned who owns what. An *artist* now owns profiles, and *members* are the Google accounts that work on one. Admins are still whoever is in `ALLOWED_EMAILS`, and they see everything. Migration 0006 moves Jarred's existing profiles under an artist called Synman; on an empty database it creates nothing, so a stray artist never shows up in a fresh test database. The migration can't create user rows, though, because `ALLOWED_EMAILS` lives in Vercel, not the database, so a user is written the first time someone actually signs in. A new People page lets admins add, rename and remove members instead of editing `ALLOWED_EMAILS` and redeploying, and Run now and the Claude budget became admin-only, because they spend everyone's money.

Stage 1 stops short of the goal, though, and that matters. It enforces sign-in and those admin-only actions, and re-checks access on every request rather than caching it in a cookie, so being removed from your last artist stops you on your next click. But nothing in stage 1 alone filters profiles, the digest or verdicts by artist: on its own it would have let any signed-in member see and edit every artist's work. That filtering is stage 2, and once a review pointed out the gap, Jarred chose to hold stage 1 back and ship the two together. So that window never existed in production.

Review before shipping caught three things that would have shipped otherwise. First, sign-in lowercased the incoming email before checking it for ASCII look-alikes, which defeats the point of that check: the Kelvin sign, written here as the escape `\u212a` (six ASCII characters in the source, one character once decoded), lowercases to a plain "k", so a crafted address could have matched a real member's email once both sides were folded to lowercase. The check now runs on the address as Google sent it. Second, the runner status panel was about to show every signed-in member the same raw pipeline error text admins see, and that text can name another artist's playlists or curators. Members now get one generic line instead. Third, the People page updated its results but left keyboard focus wherever it had been, so a screen-reader user got no indication that Add, Rename or Remove had done anything; results are now announced by moving focus to the new content or the first error.

One more change is structural rather than a feature: `pyproject.toml` now promotes every SQLAlchemy `SAWarning` to a test failure, not just a printed line. The prompt was a "cartesian product" warning: a query across artists, profiles and members that forgets a join doesn't just run slow, it can return every artist's rows instead of one, which is exactly the shape of bug this stage exists to prevent. Better to fail the test than leak the rows.

Stage 2 put every route behind the same question: is this on one of your artists? Profiles, profile editing, Ask Claude, the digest and verdicts all ask `core/access.py`, and anything on another artist answers 404, exactly like something that doesn't exist. The order is deliberate. Visibility is checked *before* a route validates what it was sent, so another artist's profile answers 404 even for a nonsense move direction or an Ask Claude section that doesn't exist. A 400 there would confirm the profile is real. If that ever looks like a bug worth "fixing" back to 400, it isn't.

The safety net is `tests/test_web_access.py`. Signed in as someone on a different artist, it calls every registered route with real ids from the other artist's data. It expects 404 for anything of theirs, 403 for admin-only actions, and 200 on the outsider's own pages, which must show the outsider's own profile and digest entry and nothing of the other artist's. It fails if a route is added without being listed in `tests/route_walk.py`, or if a mounted sub-app hides routes it can't see. Its sibling `test_web_access_sweeps.py` walks everything again as someone who was just taken off their only artist, then with ids too big for Postgres, spoiled all at once and one at a time, where the answer must be not found, never a crash. Reviews along the way found write routes that could answer 404 *after* they had already committed, so the walk doesn't trust status codes. Each write route gets a fresh world, seeded so the route would really change something (a profile is active before `pause`, and has two genres before `move`). The test then snapshots the other artist's data, plus the budget, the People lists and the run queue, and compares them afterwards. A second review caught that one combined walk could let a later leak undo an earlier one, which is why each route is checked on its own. `test_web_access_controls.py` is the other half of that check: an admin calling each write route with the same ids and form must change the snapshot, so no route can pass just because its call was a no-op. To prove it wasn't just passing, we deleted one `require_outreach` line and watched it fail. Then we moved one profile check to after the commit, so the route still said 404, and watched the snapshot catch the change the status code hid. One surprise: FastAPI 0.141 nests included routers, so the plan's "list `app.routes`" found just two routes. The walk flattens them with `iter_route_contexts` instead.

One known gap stays open until stage 3. A member's Bad fit or Dead verdict still sets `curators.excluded_at`, which hides that curator from every artist's digest and research, not just theirs. We accepted that rather than make those verdicts admin-only: it's rare while the 90-day window is still app-wide, and it leaks nothing. If a mark was wrong, clearing `curators.excluded_at` and `exclusion_reason` for that curator reverses it.

## 2026-09-16 (later): Tables for pitching by email

Migration 0007 lays the ground for pitching curators from inside the digest. Nothing reads or writes these tables yet; this is only the shape. The decision worth recording is who owns a mailbox. It belongs to an **artist**, not to the app and not to a profile, which is what lets a second artist join without sharing Jarred's inbox, and lets two of one artist's profiles pitch from the same address.

Saying that in English is easy; making the database refuse the alternative is the interesting part. `mail_accounts` carries a redundant-looking unique constraint on `(id, artist_id)`, which exists purely so `profiles` can aim a *composite* foreign key at it: `(mail_account_id, artist_id)` must match a real `(id, artist_id)` pair. A profile pointed at another artist's mailbox is then rejected by Postgres itself, not by a check someone can forget to write in a route. `outreach` also records the mailbox a pitch went out from, rather than reading it off the profile, so replies keep threading even after that profile switches address. Profiles gained `open_conversation_limit` and `quiet_after_days` now, while the table was being altered anyway, so the digest can work to them later without another migration.

Two things surfaced that the plan had wrong, and both are worth remembering. The test meant to prove the `direction` check constraint fed it the value "sideways", but that column is `varchar(3)`, so Postgres rejected it for *length* and raised `DataError` rather than the `IntegrityError` the test asked for. The constraint was never exercised. A three-character bad value ("up") fails the way the test intended. The second is still open: the composite foreign key says `ON DELETE SET NULL`, and Postgres applies that to *both* its columns, so deleting a mailbox a profile still points at tries to null `artist_id`, which is NOT NULL, and dies with a confusing `NotNullViolation` instead of tidily letting go. Nothing deletes mailboxes yet, so it costs nothing today. When something does, the fix is `ON DELETE SET NULL (mail_account_id)`, which Postgres has supported since 15 — and disconnecting a mailbox should probably stamp `disconnected_at` rather than delete the row at all, which is why the column is there.

## 2026-09-16 (later still): A small Gmail client

`core/gmail.py` is the second piece of the pitching feature and still nothing calls it. It holds a refresh token the caller has already decrypted, swaps it for a short-lived access token, caches that in memory, and exposes exactly five calls: `profile`, `send`, `history_since`, `message`, `thread`. It lives in `core/` rather than `pipeline/` because both halves of the system need it — the Vercel web app sends, the Mac Mini runner reads replies — and so it depends on nothing heavier than httpx. It is modelled deliberately on `pipeline/web.py`, down to the explicit per-request timeout and the error type carrying a `kind`.

That `kind` is the whole point of the module. An HTTP status code is the wrong thing to hand a route, because three of Google's refusals mean three unrelated things to a person. `auth` (a refused refresh token, a 401, a 403) means a human must reconnect the mailbox and no amount of retrying will help. `transient` (429, any 5xx, a dead socket) means try again later. `rejected` means Gmail understood perfectly and said no, so retrying sends the same bad message again. And `history-gone` — a 404 from the history endpoint specifically, because Gmail forgets history older than about a week — means the caller should stop asking what changed and re-read whole threads instead. Sorting those once, here, keeps four different recovery strategies out of every future caller.

The security property is enforced by two tests rather than a comment: no refresh token, access token, address or message body may appear in an error message. Network failures therefore name only the exception's *type*, never httpx's own text, which happily includes the URL; and a failed API call names only the path segment it was calling ("messages", "history") with every id stripped. Keep that true of any logging added later. Two soft spots are worth knowing before Task 4 builds on it: `send` reads `id` and `threadId` straight out of the response, so a shape Google has never actually returned would escape as a bare `KeyError` rather than a `GmailError`, and `response.json()` on a non-JSON 200 (a captive portal, an HTML error page) would raise `ValueError` the same way — `pipeline/web.py` guards that case in `WebSearch` and this module does not. Neither is reachable from the tests; both would be cheap to close the first time a caller cares.

## 2026-09-16 (evening): The message itself

`core/mime.py` is the third piece of the pitching feature and, like the two before it, nothing calls it yet. It does two small things in opposite directions: `build_message` turns a from, a to, a subject and a body into the base64url MIME blob `Gmail.send` wants, and `parse_message` turns the nested payload Gmail gives back into the handful of fields Noble Hunter stores.

It is plain text and nothing else. No attachments, no HTML alternative, no tracking pixel. That is partly taste, since it's what a curator's inbox wants from a stranger, and partly what keeps the module small enough to hold in your head.

The reason it's a file of its own rather than four lines inside the send route is header injection. A newline inside an address or a subject ends that header and starts a new one, so an address typed into a form could carry `\nBcc: somebody@else.com` and quietly copy a third party on every pitch. `_header` refuses any value holding `\r` or `\n` before `EmailMessage` ever sees it, so the refusal is ours and predictable rather than whatever the standard library happens to do this release. The body is deliberately exempt: a line reading `Bcc: this is just text` is just text, and a test insists it survives.

The other half is quoted history. A reply usually carries the whole thread underneath it, so `parse_message` splits at the "On <date> … wrote:" line, and at the couple of other separators clients use, and keeps what a person actually wrote apart from what they merely quoted. Otherwise a conversation would show the same paragraph five times down the page.

The test that earns its keep is the round trip. Gmail hands our own sent messages back through the reply sync, so anything we build has to survive being parsed by the same module. Build it, decode it, feed its body back through `parse_message`, and the original body must come out. `set_content` adds a trailing newline and `get_content()` returns it, which is why `_as_text` strips.

Two things in the plan were wrong, and both were in the test rather than the code. The `sent_at` assertion paired an `internalDate` of `1_789_000_000_000` with 2026-09-06 22:26:40, but that epoch is really 2026-09-10 00:26:40; the asserted time would need 1788733600, which is nobody's round number. The round epoch was plainly the deliberate half, so the date literal was corrected rather than the assertion loosened. And the round-trip test called `message_from_bytes(...)` then `.get_content()`, which the legacy `email.message.Message` doesn't have — `get_content` arrived with `EmailMessage` — so the parse needs `policy=policy.default`. No change to the module could have fixed that one.

## 2026-09-16 (late evening): Whose mailbox is it

`core/mailboxes.py` is the fourth piece of the pitching feature and the first one a person will feel. It connects a Gmail mailbox to an artist, lends it to that artist's profiles, and takes it back. Task 6's routes and the Google consent screen sit on top of it; nothing in here talks to Google at all. `connect_mailbox` is handed a refresh token the route has already obtained, which is exactly what lets the whole module be tested without a network.

The rule it exists to state is the one migration 0007 already enforces: a profile may only pitch from its own artist's mailbox. The database refuses the alternative with a composite foreign key, and this module refuses it earlier, in a sentence. Both were kept deliberately. The constraint is the half that will still be true after someone writes a route that forgets to ask; the message is the half a person can act on, because Postgres's version of that complaint names a constraint rather than a mistake.

Connecting the same address twice refreshes the existing row instead of adding a second one. Google issues a brand-new refresh token every time someone walks through consent, and the old one may already have been revoked from their account page, so a second row would be a second, silently dead copy. Reconnecting is also the *repair* path: it clears `needs_reconnect`, `last_error` and `disconnected_at` together, so the mailbox that has been failing all week is fixed by precisely the action a person would guess.

Letting go is the subtle one. `detach_mailbox` returns the mailbox only when no profile still points at it, and that return value is a signal to the caller — "nobody uses this, you may revoke it at Google" — not something this module acts on. Nothing revokes anything yet. The ordering inside it is load-bearing: the profile is detached and flushed *before* the "is anyone still using this?" query runs, so the profile letting go doesn't count itself and a single-profile mailbox would never be handed back at all. Only then is the stored token cleared and `disconnected_at` stamped. The row itself stays, because `outreach` and `email_messages` still point at it under `ON DELETE RESTRICT`, and because past conversations should keep reading correctly forever.

Two refusals in here look alike and aren't. Another artist's mailbox is a permissions problem; a disconnected one is a state problem. Both raise `MailboxProblem`, and the tests match on distinct phrases so the two can't quietly collapse into one vague message.

One loose end for Task 6. `connect_mailbox` finds an existing row case-insensitively with `func.lower`, but the unique constraint is on the raw address, and there is no functional index behind it, so nothing at the database level stops `Synman@gmail.com` and `synman@gmail.com` both existing for one artist. If they ever did, the lookup's `scalar()` would pick one arbitrarily rather than complain. Reconnecting also keeps whichever spelling was stored first, never the new one. Neither is reachable through this module alone, which is the only thing writing that column today, so nothing was changed. But the rest of the codebase lowercases an address before storing it (`core/people.py`, `core/access.py`, `core/contacts.py`), and that is the cheap fix the moment a route writes an address by some other path.

One more for Task 9, which has to send. Two unrelated exception families sit behind "I couldn't get a token". `refresh_token_for` raises `MailboxProblem`, a `ValueError`, when the mailbox isn't connected any more; `core/mail_crypto` raises `MailNotConfigured`, a `RuntimeError`, when the key is missing or can't read what's stored. The sender must catch both, and they deserve different words: reconnect this mailbox, versus this machine isn't configured to send at all.

## 2026-09-16 (night): The Pitch mailbox card

This is the task where mailboxes stop being a table and start being something a person can click. A profile page now carries a Pitch mailbox card, and behind it four routes: start Google's consent flow, handle the callback, attach one of the artist's existing mailboxes, and disconnect. `web/mail.py` is deliberately thin. Every rule it needs already lived in `core/mailboxes.py`, and it adds none of its own.

The thing worth understanding is why connecting is a *second* trip to Google. Signing in asks for a name and an email; this asks for `gmail.send` and `gmail.readonly`, which is a different consent screen with a different answer. It also asks with `access_type=offline` and `prompt=consent`, because Google only issues a refresh token when consent is genuinely fresh — a silent re-approval hands back an access token and nothing worth storing, which is exactly the case `GoogleMailExchange` refuses rather than storing an empty string.

That round trip is also the security-sensitive part, since an OAuth redirect is a request the app didn't originate. Before sending anyone to Google, the route puts a random `token_urlsafe(32)` and the profile's id in the session. The callback compares the returned state with `secrets.compare_digest`, pops the pending entry before anything is stored, and then asks `require_profile` all over again. Anything that doesn't match — a wrong state, a session with nothing pending, someone else's profile — is a 404, the same answer this app gives for everything a viewer may not see. The access walk leans on that: `/mail/callback` carries no ids, so an outsider's walk is precisely a request with nothing pending.

Three things in the plan turned out to be wrong, and all three were caught by tests rather than by reading. The first: the plan passed the "Google couldn't connect that mailbox" sentence through the template context, and Jinja's autoescaping renders that apostrophe as `&#39;`, so the page would have shown mangled text and the test asserting on the sentence would have failed. The sentence now lives in the template as literal text and the context carries only a flag; interpolated notices (which can contain a Gmail address Google supplied) stay escaped, as they must. The second: the plan's new line in the route walk's `call` filled *every* form value through `str.format(**ids)`, which quietly corrupted the Ask Claude choice, a JSON string full of braces. Only a value that is exactly `{some_id}` is a placeholder now. The third: `model_copy(update=...)` skips pydantic validation, so a test handing it a bare string put a `str` where the app expected a `SecretStr` and every mail route answered 500. The fix belongs in the tests, not in a `hasattr` dance in production code.

One change the plan didn't list was needed in `tests/test_web_access_controls.py`. That file asserts an admin gets 200 on every GET in the walk, and two of the new GETs aren't pages: connecting redirects to Google (303) and the callback has nothing pending for an admin who never started one (404). The access world also gained a `MAIL_TOKEN_KEY`, which matters more than it looks: without one, an admin's request to connect would 404 too, for a completely unrelated reason, and the positive control would have been proving nothing. With mail configured, the admin gets a 303 where the outsider gets a 404, and the difference is the access check.

Two seams are left for the tasks that follow. `app.state.mail_exchange` is the swappable half of Google, so no test ever touches the network; and `cipher_or_none` is the one place that answers "can this deployment read a stored token at all", which sending (Task 9) and the inbox (Task 13) must both agree with. `GoogleMailExchange.for_redirect` returns a *copy* rather than mutating itself, because the instance on `app.state` is shared by every concurrent request and Google refuses a code presented against a different redirect URI than it was issued for. Still nothing revokes anything at Google: disconnecting clears the stored token and stamps `disconnected_at`, and the refresh token stays alive at Google's end until someone removes it from their account page.

## 2026-09-16 (very late): Claude writes the pitch

`core/pitch_writer.py` is the third Claude caller in this codebase, and the most interesting decision about it is how little it invents. It is deliberately a sibling of `core/suggestions.py` and `pipeline/fit_judge.py`, down to the shape of the call: one structured-output request, thinking off, low effort, a bounded answer, a `Protocol` so no test ever touches the network, and one exception type whose message is safe to put on a page. A reader who knows either of the other two already knows this one. That sameness is worth more than any cleverness a drafting prompt could have earned.

The sentence to hold onto is that the pitch is Jarred's letter, not Claude's. Claude sees exactly what the digest already shows him — the brief, the suggested angle, the tracks, the artists the music sits next to — plus whatever he typed into the box, which is usually three words: "shorter", "mention the Autechre track". It answers with a subject and a body, and that is the end of its involvement. Nothing in this module sends anything; `core/pitches.py` does that, only when he presses Send, and only after he has edited what came back. The `SYSTEM_PROMPT` is therefore the actual product here: plain English, six sentences, no flattery, no hype, no bullet points, easy to say no to. It reads unprofessionally on purpose, because that is what a stranger's email has to read like to get answered.

`template_pitch` is the safety net, and its one rule is that it must never raise, whatever is missing. Give it nothing but a playlist name and a URL and it still produces a greeting, a sentence and a sign-off. That exists so a flaky API never leaves a person staring at an empty box — a plain draft he rewrites is strictly better than a blank one plus an error. It is also the reason the error path is worth reading: a refused call and an unreadable answer both raise `PitchWriterError`, and the page keeps whatever draft was already in the box rather than clearing it.

Where this module differs from its siblings is the import at the top. It needs `cost_of`, which lived at `pipeline/llm_costs.py` until the previous commit moved it to `core/llm_costs.py`. Nothing in `core/` or `web/` may import `pipeline/` — the web app runs on Vercel and the pipeline never does — and `tests/test_architecture.py` now fails loudly if anything tries. The web app instantiates `ClaudePitchWriter`, so this was the exact boundary that nearly rotted. Importing from `core/` is not a stylistic preference here; it is the whole reason the helper moved.

One deviation from the plan, in the live test. The plan invented a `NOBLE_HUNTER_LIVE` environment variable, but this repo already answers that question its own way: live tests carry `pytestmark = pytest.mark.live` and `tests/conftest.py` skips them unless `--run-live` is passed, exactly as `tests/test_suggestions_live.py` and `tests/test_spotify_live.py` do. A second, parallel mechanism for "don't call the real API" would be a trap for whoever added the third one. The file follows the existing pattern, key lookup included.

Two things for the tasks that follow. Task 9's compose panel needs to catch `PitchWriterError` and nothing else from `write` — a malformed response, a missing `content`, a non-JSON body and a network refusal all arrive as that one type — and should reach for `template_pitch` rather than showing an empty editor. And a note for whoever first runs the live test with `--run-live`: this call sets `thinking: {"type": "disabled"}` to match its two siblings, which is accepted on Opus 5 at low effort, but that model can occasionally leak reasoning into visible text when thinking is off. Structured output makes it very unlikely here, since the answer is schema-constrained JSON. If a draft ever comes back with stray tags in it, that is the thread to pull, and the fix is low effort with thinking left on rather than a new prompt.

## 2026-09-16 (later): Sending, and the one definition of "used up"

`core/pitches.py` is the domain half of email pitching: which address a pitch goes to, the draft that survives a closed tab, the send itself, and the thread it becomes. No web anywhere in it, which is the point — Task 9's panel will be thin for the same reason `web/mail.py` was.

The decision worth keeping is that sending does not set a status. It calls `core.exclusion.record_verdict`, exactly as the Pitched button does. There is one definition of a curator being used up for 90 days, and an emailed pitch has to mean precisely what a hand-recorded one means, or the exclusion rule quietly grows a second personality. `record_verdict` also stamps `pitched_at` and, for the permanent verdicts, excludes the curator — none of which a `status = "pitched"` assignment would have done.

The ordering inside `send_pitch` is load-bearing, not stylistic. Clean the text, check the send key, refuse a ruled-out curator, resolve the address — and only then call Gmail, and only then write anything. A failed send must leave no `EmailMessage` row, no thread id and no status change, because the alternative is an entry that claims it pitched a curator who never heard from us, burning them for 90 days over a 500 from Google. The test that pins this asserts the row count is zero, which is the assertion that would catch a future refactor moving the write above the call.

`_refuse_if_ruled_out` lives in this module rather than in the route, and that placement is the whole rule. The verdict buttons and the compose panel can both reach the same entry, in either order; putting the refusal next to the send means a curator marked bad-fit stays unwritten-to no matter which arrived first, and an entry already at `bad-fit` is never quietly downgraded to `pitched`. A check in the route would only have covered the orders the route happens to see.

`_clean` is deliberately shared by saving and sending, so a draft that can't be saved can't be sent either — there is no path where an empty body sneaks out because it took the other door.

One defect in the plan's own test, caught by the database rather than by reading. `test_it_replies_to_the_curators_last_message` built a *second* `FakeGmail` for the reply, and the fake numbers its messages per instance, so the reply came back as `msg1` again and hit the unique constraint on `(mail_account_id, gmail_message_id)`. Reusing the one fake fixes it, and the assertion moves to `gmail.decoded(1)` — which is why `decoded` takes an index at all. The constraint did its job: two different messages may never share a Gmail id in one mailbox.

Two things for what comes next. `_last_incoming_id` reads `rfc822_message_id`, which nothing writes yet — Task 10's sync fills it in as messages come back from Gmail. Until then the first pitch has nothing to reply to, `In-Reply-To` is absent, and Gmail's `threadId` alone keeps our own follow-ups together; that is correct for us and invisible to the curator, but a *reply* only threads properly in their client once the sync is running.

The second is a sharper edge. `pitch_address` falls back to any email contact ordered by confidence when the best contact isn't an email, and that fallback has no grade filter — so a curator whose only email is grade C is pitchable. `core/contact_routes.py` says C is never used, and the research prompt defines C as "only the name matches": an address nobody confirmed belongs to this curator. Sending there is a real email to a possibly uninvolved stranger. It is left as the plan specified it, with no test either way, but whoever builds the compose panel should decide deliberately whether to filter the fallback to A and B or to show the grade next to the address before Send is pressed.

## 2026-09-16: The compose panel, where the feature becomes usable

This is the task where all the previous ones turn into something Jarred can click. Every digest entry now carries a "Write a pitch" disclosure, and behind it four routes in `web/pitches.py`: read the panel, ask Claude for a draft, save it, send it. Like `web/mail.py` before it, the module is deliberately thin. `core/pitches.py` already decides who may be written to, what a valid draft is, and what sending means; the web layer adds no rule of its own, and the only thing it really owns is what a person reads when something goes wrong.

The panel loads on its own, the first time the disclosure is opened — `hx-trigger="toggle once from:closest details"` against a `<div>` that starts life holding the word "Loading…". That is not a flourish. A digest is twenty entries, and the panel needs the curator's best email, the profile's mailbox and the entry's whole message thread. Rendering that eagerly would have turned one page into sixty queries to serve a panel nobody opened. Deferring it keeps the digest exactly as cheap as it was yesterday, and the cost lands only on the entry actually being written to.

Sending is the one route in this app that touches the outside world, and it needs three things at once: a mailbox on the profile, an email address for the curator, and a draft with something in it. The shape of the route is therefore mostly its failure branches, and each of them says which of the three is missing rather than failing. A missing mailbox links to the profile page that can connect one. A curator with no usable address says so and points back at the contact route on the card. Google refusing the token marks the mailbox `needs_reconnect` and says to reconnect it — the one case where a person's next action is somewhere else entirely. A stored token this key can't read says the same thing, because reconnecting is genuinely the fix, and because the alternative was a 500 for something entirely explicable.

Every one of those branches rolls back before it re-renders. `core/pitches.py` already guarantees no row is written before Gmail accepts the message, so the route's only job is to not leave a half-finished transaction behind and to hand back the draft the person had typed. That is why `_panel` takes `subject` and `body` at all: a refused post re-renders with what was in the box, not with what the database last agreed to.

Pressing Send twice is the failure nobody reports but everybody causes. The panel renders a fresh `send_key` into a hidden field; `send_pitch` refuses a key it has already seen, and the unique index on the column catches the case where two genuinely concurrent posts both pass the read-then-write check. Both paths end at the same sentence — "Sent." — because both are true. The second press did not send a second email, and telling someone their double-click was an error would be worse than useless.

The out-of-band swap is the small piece of interface design worth recording. When a send succeeds, the entry card is still on screen with its old status, and reloading the digest to fix one word would throw away everyone's scroll position and every open panel. So the status tag is now *always* rendered, carrying `tag--empty` (and `display: none`) when there is no verdict yet, and the send response swaps it by id with `hx-swap-oob`. A tag that only exists once it has something to say has no id to aim at. That is the whole reason `tests/test_web_digest.py` stopped asserting on `class="tag tag--status">Pitched` and now asserts on the id: the markup changed for a reason, not by accident.

One defect found reviewing my own diff rather than by a test: that out-of-band tag originally hardcoded the word "Pitched". `send_pitch` correctly refuses to walk an entry backwards from `replied` or `placed`, but the panel would cheerfully have swapped the card's tag to "Pitched" anyway, so the page and the database would have disagreed the moment Task 10's replies land. It now renders the entry's actual status through `VERDICT_LABELS`, falling back to the status itself for the two labels the verdict buttons don't offer.

Three deviations from the plan, all in the access walk, and all the same underlying mistake. The plan treated the walk's two clients as interchangeable, and they are opposites. `_RefusingGmail` — whose `send` raises rather than opening a socket — is exactly right for the outsider, where any send reaching Gmail means something leaked past `require_outreach`. Given to the *admin* it would have broken `test_an_admin_calling_the_same_write_route_does_change_something`, which calls every write route as someone who is allowed, and needs the send to actually land. The admin therefore gets a recording `FakeGmailSender`, and its send is the positive control: an `EmailMessage` row and a `pitched` status, which is why `their_data` now snapshots both. The same reasoning applies to the pitch writer — test settings carry no `ANTHROPIC_API_KEY`, so without a `FakePitchWriter` the Draft-it route would have changed nothing and its control would have failed for a reason that had nothing to do with access. The third was smaller: the plan's snippet added a mailbox to the access world that `build_world` had already created two tasks ago, which would have tripped the unique constraint on `(artist_id, address)`. Only the curator's email contact was actually missing.

Three things for what comes next. Task 13's Inbox fetches this same panel at `/outreach/{id}/pitch` and renders it outside a digest card, which is why `playlist_name` and `curator_name` sit in the context unused today — standalone, the panel has to name what it is about. `_RefusingGmail` keeps its name because Task 13 extends it with reads. And the thread at the bottom of the panel renders `EmailMessage` rows that only Task 10's reply sync will ever write; today it shows exactly one message, the pitch we just sent.

The grade-C question the last entry left for this task is still open, and deliberately so. The panel shows the address it would write to, in bold, immediately above the Send button, and asks for confirmation naming that address — so an address nobody corroborated is at least visible before anything goes out. It is not yet *labelled* as uncorroborated, and `pitch_address` still has no grade filter on its fallback. Showing the grade next to the address is the cheaper half of that fix and belongs with the next piece of contact work, not here.

## 2026-09-16 (latest): Replies come back, and the rest of the mailbox stays shut

Pitches have been going out since Task 8. `core/mail_sync.py` is how they come back. It is small, and almost all of its design is about what it refuses to read.

The mailbox is Jarred's own Gmail. His bank is in there, his family, the rest of his working life. So the rule the module is built around is that a message is matched to an outreach entry *before* it is fetched, not after. `_threads_we_know` turns the entries pitched from this mailbox into a map of Gmail thread id to outreach id; a message whose thread isn't in that map is counted as ignored and dropped on the spot. It is never requested, never parsed, never stored. The test that pins this asserts `gmail.fetched == []`, and that empty list is the actual feature — an assertion on the database alone would have passed just as happily while the code read every message in the mailbox and threw most of them away. The ordering is the promise, so the assertion has to be on the ordering.

Gmail's history API makes this cheap enough to ask every few minutes: it answers "what changed since id X" rather than handing back an inbox. The catch is that Google keeps roughly a week of history and then forgets, and a runner that was off over a holiday would come back to an id that no longer resolves. That is not a failure and is not treated as one. `_changes` catches the `history-gone` kind specifically, re-reads only the threads we already know about, and takes a fresh history id from the profile call so the next run has somewhere to start from. Every other `GmailError` is re-raised, because "I couldn't tell what changed" and "Google refused your token" must not share a recovery path.

Nothing in here raises for an ordinary problem. Each mailbox returns a `SyncOutcome`, and `sync_all` catches even a failure to *open* a mailbox, because one artist's revoked token must not stop another artist's replies from arriving. An `auth` failure is the one that needs a person: it marks the mailbox `needs_reconnect` and deliberately leaves `history_id` alone, so that whatever arrived while the token was dead is still waiting to be read once someone reconnects. Advancing the id there would have silently swallowed exactly the messages the outage covered.

The guard at the top of `_store` is the least obvious line in the file and the one most worth keeping. `core/mime.py`'s `parse_message` is deliberately forgiving — a malformed payload comes back with an empty id and a 1970 date rather than an exception. That is right for parsing and wrong for storing. Without the guard a broken message would be written with a `sent_at` of 1970, which sorts before every real message in the thread and, being incoming and unread, would sit in the Inbox's count forever with no way to age out. Refusing it here costs one `ignored` and loses nothing real.

Two smaller things a later task will meet. A message that is already stored counts as neither `stored` nor `ignored` — running the sync twice reports zero of both, which is the honest answer, but anything displaying those numbers should not expect them to add up to the size of the history. And a successful sync clears `needs_reconnect`, since a mailbox that just answered plainly does not need reconnecting; but `sync_all` skips flagged mailboxes by design, so in practice only Task 13's "Check now" — which calls `sync_mailbox` directly — can ever clear that flag. That asymmetry is intentional, and it means the Inbox button is also the recovery path.

One defect in the plan's own test text, caught by Postgres rather than by reading it. The helper that builds a pitched entry hardcoded `make_artist(session, "Synman")`, and `artists.name` is unique, so the two `TestAllMailboxes` tests that build a second entry died on a `UniqueViolation` before reaching a single assertion. The fix names the artist after the thread, which is already what distinguishes the two entries — and it is the right shape anyway, because those tests need two *mailboxes* to sync, and a mailbox belongs to an artist. The plan also predicted 14 tests where the file contains 15; the suite is 1664 passed, 6 skipped.

What comes next inherits a working reply path. Task 11 runs `sync_all` on a timer from the Mac Mini and will need to decide how loudly to report a mailbox that keeps failing, since nothing here raises. Task 12 reads the rows this writes to show mail state on a digest entry — and `rfc822_message_id`, which Task 8 read but nothing wrote, is finally populated, so a reply now threads properly in the curator's client rather than only in ours.

## 2026-09-16 (later): The runner reads the mail, on a thread of its own

Task 10 taught Noble Hunter what a reply is. This task is about when it finds out. Nobody is looking at the digest page at 7am, and a Vercel function lives for seconds, so polling Gmail from the web app was never on the table. The Mac Mini already wakes every minute under launchd, so the mail goes there.

The decision worth recording is that it does *not* go into the run loop. `keep_reading_mail` is a background thread ticking every five minutes, modelled line for line on `keep_checking_in`, and `run_forever` now wraps its whole loop in it. A nightly run can take an hour — discovery, Chromium, Claude — and replies arriving during that hour shouldn't have to wait for it to finish. The symmetry matters in the other direction too: the thread catches and logs every exception, so a mailbox that can't be read never becomes a run that failed. `sync_mail` defaults to `None` and the wrapper is `nullcontext()` when it isn't given, which is why `tests/test_worker.py` needed no changes at all — a runner with no mail keys behaves exactly as it did yesterday.

That "catches every exception" is also the trap this task had to work around. `core.mail_sync.sync_all` deliberately never raises: it collects each mailbox's failure into a `SyncOutcome` and carries on, because one artist's dead token must not stop another artist's replies. Perfectly correct, and it means a runner watching only for exceptions would report a permanently broken mailbox as a clean round, every five minutes, forever. So `sync_round` reads the outcomes it gets back and logs its own summary — at `warning` when any outcome carries an error, `info` otherwise. The log is the only place this surfaces today, which is precisely what Task 12 is for.

Everything in a round is built and thrown away: the httpx client, the cipher, the `Gmail` objects, the session. That isn't tidiness, it's the Mac Mini sleeping. A long-lived HTTP client on a machine that suspends at night is a pile of dead sockets waiting for the morning.

`PipelineSettings` doesn't inherit from `core.settings.Settings`, so the three mail values had to be added to it by hand, and `mail_problem()` returns the names of whichever are missing rather than a bare boolean. Missing keys are not an error: `sync_round` logs one line and returns `{}`, and the runner does everything else exactly as before. A Mac with no mail keys is a supported configuration, not a broken one.

One deviation from the plan, and one defect in it. The plan's CLI test leaned on a `runner` fixture that doesn't exist here — the CLI tests in this repo build `CliRunner()` inline and use `pipeline_env` plus `monkeypatch.chdir(tmp_path)` to keep the repo's real `.env.local` out of reach — so the test was rewritten to match its neighbours. The plan also warned that `google_client_secret` as a *field name* would trip a repr assertion on the bare word "secret"; in this repo that assertion is on `"pipesecret"`, so there was nothing to fix.

The defect I did fix was my own to find, reviewing the diff. `mail_problem()` only checks that the three values are *present*. A `MAIL_TOKEN_KEY` that is present but truncated — a paste that lost its tail, or a half-finished rotation — sails straight past it and dies inside `mail_cipher` as a `MailNotConfigured` traceback out of `pipeline.cli mail`. Every other command in that file turns its failures into a sentence, so this one does now, with a test. That is the single extra test beyond the plan's arithmetic: 1669 passed, 6 skipped, where the plan predicted 1668.

Two things for what comes next. Task 12 wants mailbox trouble in the runner panel, and the durable material is not what this thread holds: `sync_round` returns `dict[int, SyncOutcome]` and then logs it and forgets it. The thing that survives a restart is `MailAccount.needs_reconnect`, which `sync_all` sets, and that is what a panel should read. And the mail thread's shutdown join is `timeout=every` — five minutes, where the heartbeat's is thirty seconds. The thread is a daemon so nothing hangs forever, but a SIGTERM landing mid-round can leave the runner up to a round late in exiting.

## 2026-09-16 (last): The mail finally shows on a screen

Eleven tasks built a mail stack nobody could see. Pitches went out, replies came back, the runner read them every five minutes — and the only evidence of any of it was a log line on a Mac Mini under a desk. This task is the two places a person actually looks.

The first is the digest entry. `EntryMail` hangs off `EntryView` and says four things: how many we sent, how many came back, who spoke last, and when. `waiting_on_you` is a property over `last_direction`, not a column, and that is the decision the whole thing rests on. ## 2026-09-16 (evening): The Inbox, or who is waiting on you

The digest answers one question — who should I write to tonight. It has never been able to answer the other one, which is the question you actually have at nine in the morning with a coffee: who is waiting on me. That is the whole of this task. `/inbox` lists every conversation the viewer can see, the ones where the curator spoke last at the top, most recent first inside each group.

The decision the page rests on is what it *doesn't* do. It does not work out whose turn it is. `ConversationView.waiting_on_you` is `EntryMail(last_direction=...).waiting_on_you` — the same property the digest entry uses, imported, not reimplemented. The same instinct runs through the disclosure: opening a conversation fetches `/outreach/{id}/pitch`, exactly as the digest entry does, so there is one place a reply is read and one place an answer is sent. The `<details>` deliberately wears the digest's own `digest-entry__pitch` classes. The runner reads every five minutes, which is the correct answer for a background job and the wrong one for the minute someone is refreshing the page. ## 2026-09-16 (night): The ceiling, not the nightly number

Every night so far, the digest has worked to a flat number: twenty entries, because `digest_target` says twenty. Jarred put his finger on why that is the wrong number to work to. "I'm less worried about writing 20 emails and more about having to sustain 20 conversations." Writing is the cheap part. The expensive part is the twenty half-finished threads it leaves behind.

So `core/conversations.py` answers a different question. Not "how many should we hand over tonight" but "how many conversations are already open, and how much room is left under the ceiling". The allowance is `min(digest_target, open_conversation_limit - open_now)`, floored at zero. A profile at its ceiling takes nothing tonight and that is the system working, not the system stuck.

Two judgement calls sit in the docstring, because they are judgement calls and not facts, and someone reading this in six months should see them argued rather than inferred from a query.

The first: a conversation is an *emailed* pitch. An entry marked Pitched by hand has nobody waiting on a reply to it — there is no thread, no inbox, nothing to sustain — so it does not take up a slot. The second: a pitch nobody answered within `quiet_after_days` is over in practice and stops counting, but a conversation where the *curator* spoke last never goes quiet. That one is waiting on you however long it sits there, and time does not make it less your turn.

Nothing is stored. There is no `is_open` column and no nightly job to keep one honest, because the answer is derived from the messages every time it is asked. A reply landing at 3am changes tonight's allowance by itself, with nothing needing to be updated in the right order — the same instinct that put `waiting_on_you` on the digest entry rather than in a column, and for the same reason: derived state cannot drift from the messages, because it *is* the messages.

The query is the one piece worth explaining. It is a single `DISTINCT ON (email_messages.outreach_id)` that fetches the newest message on every entry belonging to these profiles, and the quiet window is then applied in Python rather than in SQL — the window differs per profile, and this reads tens of rows, not millions. Postgres insists the distinct column leads the `ORDER BY`, which is why the statement selects `Outreach.profile_id` but orders by `EmailMessage.outreach_id`. Get that wrong and it is a runtime error, not a quietly wrong answer.

I expected trouble from that select and did not get any. With `Outreach.profile_id` leading the columns clause it looked like SQLAlchemy would take `outreach` as the FROM and then self-join it, so I compiled the statement to SQL before running a single test. It infers the left side from the join condition, not from the column order, and picks `email_messages` correctly. Worth knowing next time the same shape appears.

No deviations from the plan text: the module, both test files and the fifteen tests went in verbatim, and ruff's only change was to pull the `loads_for` signature onto one line now that it fits. 1730 passed, 6 skipped, exactly as forecast.

Two things for what comes next, and the first is a real one. Nothing here looks at `Outreach.status`, and "the curator spoke last never goes quiet" has a trap in it. A curator who replies "not for us", on an entry you then mark bad-fit or dead, leaves an inbound last message that never ages out — so a finished conversation holds a slot permanently. Do that twenty times over a year and a profile with a limit of twenty has an allowance of zero forever, with no way to see why. That is faithful to the judgement call as written and pinned by the tests, so it stays; but Task 16 is wiring this into the night, and a silted-up profile silently producing an empty digest is the failure mode to watch for. Excluding terminal statuses from the count is the obvious fix when it bites.

The second is smaller. `ConversationLoad.full` is written and untested because nothing calls it yet — Task 16 is expected to. If it turns out nothing wants it, delete it rather than leaving a convenience nobody uses.

## 2026-09-16 (late): Two numbers the migration set, and nobody could change

Migration 0007 gave every profile an `open_conversation_limit` of 20 and a `quiet_after_days` of 14, and Task 14 taught `core/conversations.py` to read them. Neither could be changed by anyone short of a psql prompt. This task puts them on the settings form, and the only interesting decision is where the checking lives.

They go through `_validated_settings`, the same funnel the name, the digest target and the follower floor already go through. The reason is arithmetic, not tidiness: the bounds have to be stated once, because migration 0007 wrote them into the database as check constraints (`between 1 and 200`, `between 1 and 365`). If the form's idea of "allowed" and the database's ever drift apart, the form cheerfully accepts a number and the insert fails — a 500 on a page that was only asking someone to type 250. So the constants in `core/profile_rules.py` were copied from the migration after re-reading it, not from memory.

The cost of adding two settings was a return type. `_validated_settings` handed back a three-tuple, and `clean_name, target, floor, ceiling, quiet = ...` is the kind of line that reads fine the day it is written and becomes a puzzle the first time someone adds a sixth. It is now a frozen `ValidatedSettings`, which cost ten lines and made `update_profile_settings` shorter: the three optional settings are applied in a loop over their own names, because the rule for each is identical — if it came back as `None`, leave what is there.

That `None` is doing more work than it looks. `_optional` returns `None` for "the caller didn't mention this setting", which is what makes leaving a field out preserve its value; collapse it to a truthiness check and a legitimate `0` — a follower floor of zero, meaning no floor — becomes indistinguishable from silence. There is a deliberate asymmetry beside it, and it is worth naming so nobody "fixes" half of it. The core validator treats `""` as **invalid**, because a person typed nothing into a required box. `web/profiles.py` turns an empty form field into `None` before it ever gets there, meaning "leave this alone", which is what an older cached copy of the form posting without the new fields should do. Both are right; they are answering different questions.

Two deviations, both forced. The task text said to import the six new constants into `core/profiles.py`; only four are used there, and the other two would have been an unused-import lint error, so `DEFAULT_OPEN_CONVERSATIONS` and `DEFAULT_QUIET_AFTER_DAYS` stay defined and unimported — the actual defaults live on the model and in the migration. And the new page test uses the `client` fixture and `htmx_post` helper that `tests/test_web_profiles.py` already has, rather than the placeholder helper the task sketched, which does not exist in that file. 1748 passed, 6 skipped, exactly as forecast.

One thing for whoever comes next, because the task text asserts it and the code does not. The premise is that "the YAML importer, the web form and any future caller" all reach profiles through `_validated_settings` — the web form does, but `core/profile_import.py` does not. It sets `profile.digest_target` straight onto the model and never calls the validator at all, so the importer is still free to disagree about what is allowed. Nothing is broken today, because `ProfileConfig` validates the file on the way in; but the single-funnel story is one route short of true, and the two new settings are not importable from YAML at all.
